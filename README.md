# Cadavre Exquis

PWA de création collective asynchrone : des histoires en quatre cases (yonkoma), dessinées à plusieurs sur une semaine. Voir [docs/ARCHITECTURE.md](docs/ARCHITECTURE.md) pour les décisions techniques.

## Lancer

```bash
npm install
npm run dev        # http://localhost:5173
npm start          # alias de npm run dev
npm test           # tests du domaine, de l'éditeur, du routeur et des thèmes SQL
npm run build      # typecheck + build PWA dans dist/
npm run preview    # sert le build (service worker actif, installation PWA testable)
npm run icons      # régénère public/icons/*
npm run db:check   # exécute les migrations dans PGlite et vérifie règles de jeu et RLS
npm run db:themes  # imprime l'import SQL de supabase/themes.json (--seed: régénère 0012_theme_bank_seed.sql)
npm run db:apply   # applique les migrations sur le projet Supabase (SUPABASE_DB_URL requis)
```

Le service worker n'est enregistré qu'en build de production : tester l'installation avec `build` + `preview`.

## Variables d'environnement

Voir [.env.example](.env.example). Copier en `.env.local` (ignoré par git).

| Variable | Portée | Usage |
| --- | --- | --- |
| `VITE_SUPABASE_URL`, `VITE_SUPABASE_PUBLISHABLE_KEY` | client | accès Supabase; la clé publishable est publique par conception, la sécurité repose sur les politiques RLS |
| `SUPABASE_DB_URL` | outil local seulement | chaîne de connexion Postgres pour `npm run db:apply`; ne jamais la commiter |
| `VITE_VAPID_PUBLIC_KEY` | client | abonnement Web Push |
| `VAPID_PRIVATE_KEY`, `VAPID_SUBJECT`, `DISPATCH_SECRET` | serveur seulement (secrets de la fonction `dispatch`) | signature des notifications, authentification de l'appel de pg_cron |

`npm run push:setup` génère ces valeurs une fois dans `.env.local` (sans les afficher). Penser à remplacer `VAPID_SUBJECT` par une vraie adresse `mailto:`. La clé de service Supabase n'est pas à renseigner : elle est fournie automatiquement aux Edge Functions.

## Base de données (Supabase)

Trois migrations dans [supabase/migrations](supabase/migrations) :

1. `0001_init.sql` : tables, index, fonctions `join_game` et `publish_contribution`, RLS.
2. `0002_app.sql` : profil automatique à l'inscription, vue `contribution_cards`, `current_game`, chemins et sous-arbres, buckets de stockage.
3. `0003_themes.sql` : historique (anciens thèmes générés et parties 2026–2030). Ne plus le régénérer : la banque de thèmes (0011, 0012) prend le relais pour les semaines à venir.
4. `0004_notifications.sql` : file d'attente des notifications, regroupement, heures de silence, annonce du nouveau thème, réservation atomique pour l'envoi; remplace `publish_contribution` pour produire les événements.
5. `0005_png_only.sql` : supprime le projet JSON (politiques du bucket `projects`, type d'asset, colonne `format_version`).
6. `0006_discovery.sql` : `archive_weeks()` et `archive_highlights()` (lecture des archives sans limite arbitraire, jamais la partie courante ni une partie privée), ordre total de `contribution_subtree`.
7. `0007_progress.sql` : `contribution_progress()`, ce que les autres ont fait de tes dessins (suites, histoire terminée), pour « Mes dessins ».
8. `0008_replies.sql` : table `reply_reads` (état « lu » par joueur et par réponse, RLS : on ne lit et n'écrit que le sien, jamais de modification) et `unread_replies()`. Les réponses déjà publiées au moment de la migration sont considérées comme connues.
10. `0010_rewards.sql` : récompenses collectives (voir « Récompenses et tampons ») : `story_credits`, `reward_events`, `sticker_unlocks`, `sticker_rules`, `reward_config`, `credit_story()` branchée sur `publish_contribution`, rattachement des histoires déjà terminées (`backfill_story_credits()`, exécuté par la migration), `my_progress()`, `my_reward_events()`, `mark_reward_events_seen()`, `admin_revoke_story()` et `sync_reward_rules()`.
11. `0011_theme_bank.sql` : banque de thèmes (voir « Banque de thèmes »), tirage « barillet » des semaines à venir, fonctions `admin_theme_*`; supprime l'ancien secours `ensure_weekly_game`.
12. `0012_theme_bank_seed.sql` : **généré** depuis `supabase/themes.json` (`npm run db:themes -- --seed`), premier chargement de la banque.

Mise en place sur un projet Supabase :

1. Authentication > Sign In / Providers : activer **Allow anonymous sign-ins**.
2. Appliquer les migrations : soit coller les trois fichiers dans l'éditeur SQL du tableau de bord, dans l'ordre; soit ajouter `SUPABASE_DB_URL` dans `.env.local` (Project Settings > Database > Connection string) puis `npm run db:apply`.

`npm run db:check` exécute ces migrations dans PGlite avec des rôles et une RLS simulés (191 vérifications, dont 89 pour Survivor multijoueur (étapes 1 à 4) : profil automatique, partie courante, auto-continuation refusée, case 4 finale, projet réutilisé ou d'autrui refusé, insertion directe refusée, projet publié figé, signalements, notifications, archives, pagination déterministe, états de lecture des réponses). Cela ne remplace pas un test sur la vraie base; les accès réellement concurrents et le stockage ne sont pas testés.
9. `0009_admin_moderation_expiry.sql` : administrateurs (`admins`, `is_admin()`), fenêtre de vie des thèmes (`starts_at`, `expires_at`, `purged_at`), dessins masqués (`hidden_kind`), signalements (`report_contribution`, blocage des signaleurs), fonctions `admin_*`, nettoyage manuel avec aperçu, file de suppression des fichiers (`storage_deletions`), journal (`purge_log`), purge automatique (`purge_expired_games`, **désarmée par défaut**) et blocage des publications sur un thème expiré (`GAME_EXPIRED`).


## Interface (refonte rétro-console)

Direction artistique « console portable » allégée : fond crème pointillé, icônes pixel art en SVG (aucun emoji, aucun asset tiers), micro-animations désactivées si l'utilisateur réduit les animations. Les bordures épaisses, reliefs et couleurs vives sont réservés aux actions importantes (Créer, Continuer, Publier, palette) et aux dessins des joueurs; les panneaux décoratifs utilisent un trait fin.

- **Design system** : `src/ui/tokens.css` (couleurs, rayons, ombres, espacements, zones tactiles), `base.css`, `components.css`, `screens.css`, `src/editor/editor.css`.
- **Composants** (`src/ui`) : `ToyButton`, `ToyCard`, `ToyTabs`, `ToyDialog`, `ToyToggle`, `ToySpinner`, `PixelIcon` (+ `Mascot`), `ColorSwatch`, `StoryThumbnail`, `BranchNode`, `WeeklyThemeCard`, `Dock`, `ScreenHeader`, `Swiper` (feuilletage horizontal natif), `ThreadPeek` (le fil d'une histoire).
- **Principe** : « Découvre un dessin. Imagine la suite. Passe le relais ! » Les arbres, branches, profondeurs et salles restent invisibles pendant une partie normale.
- **Navigation** : dock à trois entrées, **Jouer** (bouton central, l'action principale), **Lire** et **Mes dessins**. L'accueil (`#/`) présente le thème, la phrase « À plusieurs, dessinez des histoires en 4 cases. Chacun imagine la suite du dessin d'un autre ! » et deux actions sous-titrées : « Continuer une histoire » (« Dessine la suite de quelqu'un ! », mène à Jouer) et « Commencer une histoire » (« Imagine la première case ! »); Réglages par l'engrenage de l'accueil.
- **Jouer** (`#/play`, `#/play/<case>`) : une case que le joueur peut légalement continuer dans sa salle (jamais la sienne, jamais une case finale), avec l'histoire qui la précède (cases précédentes à un tap), « À toi de dessiner la case N ! » avec le rôle de la case (1 « Imagine le début de l'histoire ! », 2 « Dessine ce qui se passe ensuite ! », 3 « L'histoire approche de sa fin ! », 4 « C'est la dernière case ! Imagine la fin de l'histoire. »), le bouton « Dessiner la suite » (« Dessiner la fin » pour la case 4) toujours visible au-dessus du dock et « Une autre histoire ». Les propositions sont tirées parmi les dessins sans suite (sinon parmi tous). Options secondaires : « Commencer une histoire » et « Parcourir les cases » (`#/browse` : niveaux 1/2/3, au hasard, pagination par 12, lecture jamais tronquée à 1 000 lignes).
- **Rien à continuer** : salle vide → « Tu es le premier à jouer ! »; seulement ses propres dessins → « En attente d'autres joueurs », avec « Inviter quelqu'un à continuer mon dessin » (partage du système ou lien copié, vers `#/case/<id>`). Aucun joueur ni contenu simulé.
- **Éditeur** : le dessin domine l'écran. Barre essentielle : annuler/rétablir, Publier, stylo, gomme, six couleurs, et une ligne de consigne « Case N sur 4 · thème de l'histoire » + rôle de la case (pour une ancienne histoire, c'est son thème d'origine qui s'affiche); quand on continue une case, « Revoir l'histoire » ouvre les cases précédentes en feuille, puis « Retour au dessin » retrouve le canevas intact. Une case 4 ne termine que sa branche : les autres versions restent continuables. Pot, sélections, déplacement, main, tailles, motifs et « stylet seulement » sont dans le tiroir « Outils », qui recouvre le bas de la zone de dessin au lieu de la rétrécir (le canevas garde sa taille) et se referme au premier trait de stylo ou de gomme. Paysage : console en colonne à droite (216 à 300 px selon l'écran), tiroir intégré à la colonne.
- Aucune fausse donnée : l'accueil n'affiche que les vraies créations de la salle, avec un état vide sinon.

## Parcours (phase C)

- **Accueil** : thème actif et délai avant le prochain (heure du serveur), Jouer, Commencer une histoire, bandeau « Quelqu'un a continué ton dessin ! » quand des réponses attendent d'être découvertes, derniers dessins de la salle. Quand la salle de la semaine est vide, quelques dessins publics de parties précédentes sont affichés comme « Archives », à lire seulement : ils ne sont jamais ajoutés à la salle ni à la partie courante.
- **Lire** (`#/read`) : histoires terminées et en cours de la semaine, accès à toutes les histoires de la semaine et aux semaines précédentes (archives).
- **Mes dessins** (`#/mine`) : « À découvrir » (seulement s'il y a des réponses non ouvertes) montre pour chaque réponse directe à l'une de tes cases ta case, une flèche et la case dessinée par l'autre joueur (trois joueurs = trois paires). Toucher une paire ouvre `#/reply/<id>` : « Voici ce que quelqu'un d'autre a fait de ton dessin ! », les deux images, « Lire l'histoire depuis le début », les autres réponses (ou fins) à la même case, les fins de l'histoire, retour à Mes dessins. « Tous mes dessins » garde toutes tes cases, une fois chacune, avec « En attente d'une suite », « 1 suite », « 3 suites » ou « Dernière case ». États vides : « Tu n'as pas encore dessiné ! », « Tes dessins attendent que d'autres joueurs inventent la suite ! », « Tu as découvert toutes les nouvelles suites ! ». Ni score, ni like, ni commentaire.
- **Pastille** : un point sur « Mes dessins » dans le dock tant qu'une réponse n'a pas été ouverte (pas de chiffre, aucune notification push ni permission). Est une nouveauté la continuation **directe**, par un autre joueur, d'une de tes cases (y compris une case 4 pour l'auteur de la case 3); une suite plus lointaine notifie l'auteur de la case parente, pas celui de la case 1. L'état « lu » est enregistré sur le serveur (`reply_reads`) quand la réponse est réellement ouverte (écran de réponse, fiche de la case ou lien d'une notification push), pas en ouvrant Mes dessins : il suit le compte sur tous ses appareils et survit au rechargement. L'état est relu au lancement, au retour sur l'application, à la reconnexion et toutes les 45 s; une erreur réseau conserve les nouveautés connues (dernier état mémorisé sur l'appareil pour la pastille) et une ouverture non enregistrée est renvoyée plus tard. La table `notifications` existante est la file d'attente du Web Push (abonnés seulement, regroupée, vidée à l'envoi) : elle ne sert pas d'état de lecture.
- **Case** : le fil jusqu'ici, « Dessiner la suite », « Toutes les suites » (vue arbre secondaire), suites imaginées par les autres, signaler.
- **Éditeur** : le dessin est soit une case 1, soit la suite d'une case. « Publier ma case » affiche une vérification (thème, position dans l'histoire, rappel de la dernière case), envoie l'aperçu PNG dans Supabase Storage, puis appelle `publish_contribution`; le serveur applique toutes les règles.
- **Après la publication** (`#/published/<case>`) : la nouvelle case apparaît à la suite des précédentes (révélation animée, sans score) avec le message adapté (« Ta première case est publiée ! », « Ta suite est publiée ! », « Votre histoire est terminée ! ») et une note qui renvoie vers « Mes dessins ». Actions : cases 1 à 3 « Continuer une autre histoire » et « Voir mon histoire »; case 4 « Lire notre histoire » et « Jouer à nouveau ». Si aucune histoire n'est continuable, « Commencer une nouvelle histoire » est proposé à la place (jamais de liste vide).
- **Histoire** : feuilletage au doigt case par case (mode par défaut sur mobile), planche 2×2, « Voir une autre suite » / « Et si l'histoire continuait autrement ? » sous chaque case, « Revenir au début », « Inventer une autre fin » (si la case précédente peut être continuée), auteurs, export PNG, partage.
- **Toutes les suites** (arbre, vue secondaire) et **Semaines précédentes** (histoires terminées, histoires inachevées toujours continuables).

Aucun brouillon : le dessin n'est conservé nulle part avant sa publication.


## Éditeur (phase B)

Bouton « Dessiner ». Une seule image 320×240 (jamais suréchantillonnée, affichée sans lissage), palette de 6 couleurs; pas de calques ni d'animation.

- **Outils** : stylo (6 tailles, 6 textures, pression), gomme (5 tailles), pot de peinture avec motifs, sélection rectangulaire et libre, déplacement, retournement, rotation, copier/couper/coller/supprimer, annuler/rétablir (100 pas, perdus au rechargement). Aucune sauvegarde ni brouillon : on dessine, on publie ou on abandonne.
- **Vue** : zoom 1× à 10× (pincement, molette, boutons), déplacement (outil Main, deux doigts, Espace+glisser), rejet de la paume pendant l'usage du stylet.
- **Publication** : l'aperçu PNG est envoyé dans Supabase Storage (seul fichier conservé). Aucun export de fichier côté éditeur. La planche PNG d'un yonkoma complet se fait depuis la page Histoire.
- **Tampons** (Outils > Tampons) : six tampons de départ (cœur, larme, étoile, couronne, petit impact, éclair) et huit à débloquer (voir « Récompenses et tampons »). Un tampon se choisit (les verrouillés disent comment l'obtenir), apparaît en aperçu au centre, se déplace au doigt, à la souris ou à l'Apple Pencil (un appui à côté le fait sauter sous le stylet), se redimensionne par multiples entiers (×1 à ×4, sans flou) puis se valide avec OK ou s'abandonne avec Annuler. Il est ensuite fusionné dans l'image comme n'importe quels pixels (palette de six couleurs, aucun calque conservé), compte pour une entrée d'Annuler/Rétablir, et la limite est de trois tampons par case (`maxStampsPerCase`). Le blanc d'un tampon peint, le transparent laisse le dessin intact.
- **Raccourcis (ordinateur)** : B stylo, E gomme, G pot, M rectangle, L lasso, V déplacer, H main, Ctrl/Cmd+Z/Y, Ctrl/Cmd+C/X/V, Entrée valide, Échap annule, +/-/0 zoom.

**Confort stylet et mobile** : réglage « Stylet seulement » (le doigt déplace la vue), blocage du zoom de page sur Safari iOS, animations d'interface désactivées si le système réduit les animations.

## Règles du jeu

- Le jeu est ouvert 7 jours sur 7. Aucune règle ne dépend du jour de la semaine.
- Chaque lundi 00:00 (Europe/Paris), le thème de la semaine devient actif, sans intervention de l'administrateur. Les anciennes histoires restent consultables et leurs branches inachevées restent continuables, avec leur thème d'origine.
- Une case 1 se crée quand on veut, dans le thème actif. Chaque continuation porte la profondeur de son parent + 1; la case 4 termine la branche.
- Aucune limite quotidienne. On ne peut jamais continuer directement sa propre case (on peut réintervenir si le parent est à quelqu'un d'autre : Alice → Bob → Alice → Chloé). Seul un débit maximal anti-abus s'applique (60 publications/heure par défaut).
- Salles de 99 participants maximum, sans emprunt de dessins entre salles. Une salle vide propose directement de créer une case 1.
- Les brouillons privés ne sont jamais proposés à la continuation.
- Événements de notification : `new_theme`, `continuation`, `new_branch`, `story_completed` (voir la section Notifications).

## Notifications (Web Push)

Désactivées par défaut : Réglages > Notifications demande le consentement, propose deux préférences séparées (rappel du nouveau thème, activité sociale) et une période de silence (heure de Paris). Le désabonnement est immédiat. Aucun rappel quotidien.

- **Événements** : créés par `publish_contribution` (continuation de ton dessin, nouvelle branche dans une histoire où tu as participé, histoire terminée) et par `enqueue_new_theme` (lundi à partir de 08:00 heure de Paris, une fois par semaine).
- **Regroupement** : les événements d'un même groupe qui attendent (2 minutes) n'en font qu'un avec un compteur : 40 suites = « 40 personnes ont continué ton dessin ».
- **Clic** : ouvre la case ou l'histoire exacte (fenêtre déjà ouverte réutilisée). Seuls des chemins internes sont acceptés.
- **Prise en charge** : jamais de simulation. Sur iPhone et iPad, le Web Push exige l'application installée sur l'écran d'accueil ; le service worker n'est actif qu'en version construite (`npm run build` puis `npm run preview`, ou site déployé en HTTPS).

Mise en service côté serveur (une fois) :

1. `npm run push:setup` (clés VAPID, secret, fichiers locaux ignorés par git), puis corriger `VAPID_SUBJECT` dans `.env.local` et relancer la commande.
2. `npx supabase login` puis `npx supabase link --project-ref <ref>`.
3. `npx supabase secrets set --env-file supabase/.env.functions`.
4. `npx supabase functions deploy dispatch --no-verify-jwt`.
5. Tableau de bord > Database > Extensions : activer `pg_cron` et `pg_net`.
6. Éditeur SQL : appliquer `0004_notifications.sql`, `0005_png_only.sql`, `0006_discovery.sql`, `0007_progress.sql`, `0008_replies.sql` puis (voir la section suivante) `0009_admin_moderation_expiry.sql`, puis le contenu de `supabase/schedule.local.sql` (planifie l'envoi chaque minute, seulement s'il y a quelque chose à envoyer, et l'annonce du lundi).
7. Rebuilder et déployer l'application avec `VITE_VAPID_PUBLIC_KEY`.

## Administration, modération et expiration

### Conservation des créations

Un thème est actif sa première semaine (lundi 00:00), reste consultable et continuable la semaine suivante comme ancien thème, puis **toutes** ses contributions disparaissent le deuxième lundi à 00:00 (Europe/Paris, calculé en dates civiles : exact autour des changements d'heure), quelle que soit leur date de publication. Exemple : thème A actif le lundi 16 novembre 2026, thème B le 23, suppression du thème A le 30. Une continuation publiée le dimanche de la deuxième semaine disparaît donc avec le reste du thème. Les parties privées ou de test n'expirent jamais d'elles-mêmes.

- La lecture s'arrête à l'échéance exacte (la vue `contribution_cards` filtre les thèmes expirés) et `publish_contribution` / `join_game` refusent tout thème expiré, même depuis un ancien onglet (`GAME_EXPIRED`) ; l'éditeur propose alors de rejoindre le thème de la semaine, sans jamais publier dans le mauvais thème. La purge physique, quelques minutes plus tard, supprime contributions, salles, états de lecture, signalements, notifications et brouillons techniques liés, puis met les fichiers du Storage en file de suppression.
- Les dates sont affichées discrètement : « Les dessins de ce thème disparaîtront le lundi … » sur la carte du thème, en Lire, sur la page d'une histoire ou d'une semaine, et dans Mes dessins uniquement pendant la deuxième semaine d'un thème (avec un rappel pour exporter les BD terminées en PNG depuis leur page).
- Concurrence : `publish_contribution` verrouille la partie en lecture puis la case parente ; la purge verrouille la partie en écriture avant de supprimer. Une publication acceptée juste avant l'échéance est supprimée avec le thème, une publication qui arrive après est refusée.
- La purge de chaque thème est une transaction à part (tout ou rien), idempotente et journalisée (`purge_log`) ; une panne laisse le thème intact et il est repris au passage suivant. La file `storage_deletions` ne marque un fichier supprimé qu'après confirmation du Storage et le reprend en cas d'échec (10 essais). Un balayage quotidien met aussi en file les aperçus de plus d'un jour que plus aucune ligne ne référence.

### Mise en service (rien n'est supprimé avant l'étape 6)

1. Sauvegarder la base (export Supabase) : la migration masque immédiatement à la lecture les thèmes dont l'échéance est passée (par exemple tout ce qui date de plus de deux semaines).
2. Appliquer `0009_admin_moderation_expiry.sql` (`npm run db:apply` ou éditeur SQL). Elle ne supprime rien et la purge est désarmée.
3. Déployer la fonction de suppression des fichiers : `npx supabase functions deploy purge --no-verify-jwt` (elle réutilise le secret `DISPATCH_SECRET` et vérifie elle-même le secret ou le jeton d'un administrateur).
4. Se déclarer administrateur : ouvrir Réglages, copier l'« Identifiant du compte », puis dans l'éditeur SQL `insert into public.admins (user_id) values ('<identifiant>');`. Rattacher une adresse e-mail au compte (Réglages) pour ne pas perdre l'accès. Personne n'est administrateur par défaut.
5. Planifier (pg_cron et pg_net déjà activés) : `select public.schedule_expiry('https://<ref>.supabase.co/functions/v1/purge', '<DISPATCH_SECRET>');` (purge toutes les 5 minutes, balayage des orphelins à 03:17, envoi de la file de fichiers).
6. Vérifier dans `/admin` > Échéances ce qui serait supprimé, puis **seulement alors** armer la suppression automatique : `select public.enable_expiry_purge();` (et `select public.enable_expiry_purge(false);` pour la désarmer).

### Administration (`#/admin`)

Réservée aux comptes de la table `admins`. Chaque fonction `admin_*` revérifie `is_admin()` côté serveur, la table `admins` n'a aucune politique d'accès, et le navigateur n'a jamais de clé `service_role` : la suppression des fichiers passe par l'Edge Function `purge`. Une condition React seule ne protège rien ; elle n'affiche que « Page introuvable » aux autres.

- **Dessins** : liste paginée avec miniatures, filtres par thème/semaine, auteur (« Mes contributions »), statut (visible, signalé, masqué, retiré, emplacement neutre) et recherche (identifiant, auteur, thème) ; masquer et rétablir un ou plusieurs dessins.
- **Signalements** : à examiner, retraits confirmés, écartés, abusifs, historique complet ; confirmer le retrait, rétablir, écarter, marquer abusif ou bloquer le signaleur.
- **Nettoyage** : sélection précise, puis aperçu chiffré (dessins supprimés, emplacements neutres conservés, suites d'autres auteurs préservées, histoires, fichiers, signalements, états de lecture, notifications). « Seulement ces dessins » remplace une case qui a encore des suites par un emplacement neutre (image supprimée, structure conservée) et supprime vraiment les autres ; « Avec toutes leurs suites » est le seul mode qui supprime aussi les dessins des autres participants. La suppression exige de taper SUPPRIMER et que l'aperçu soit encore exact (`PLAN_CHANGED` sinon). Rien n'est jamais supprimé parce qu'il appartient à un thème ou à une histoire que vous avez commencée.
- **Échéances** : prochaines suppressions par thème, état armé ou non, fichiers en attente, journal des opérations.
- **Banque de thèmes** : voir ci-dessous.

### Banque de thèmes

Les thèmes ne sont plus générés (plus de combinaison métier + adjectif, personnage, lieu). Ils viennent d'une **banque** de titres courts et ouverts, dans l’esprit des cartons de match d'improvisation, stockée en base (`themes` avec `in_bank`) et initialisée depuis `supabase/themes.json` (212 titres **originaux**, ni copiés d'une banque existante ni présentés comme des thèmes authentiquement joués : chaque thème porte sa provenance, `original`, `imported` ou `referee`). L'objectif est de pouvoir la compléter jusqu'à ≈ 520 titres (dix ans, un par semaine).

**Tirage « barillet ».** Chaque lundi 00:00 (Paris), la partie de la semaine devient active, comme avant : un seul thème partagé, aucune IA, aucun coût. Les semaines à venir (≈ dix ans, `ensure_schedule_weeks`) reçoivent leur thème par `redraw_theme_schedule()` : on retient, parmi les thèmes les moins sortis, celui dont l'empreinte `md5('barillet/v1:' || titre || semaine)` est la plus petite. C'est déterministe, et aucun thème ne revient avant que toute la banque soit passée (puis un nouveau tour commence). Le carton de la semaine suivante (qui commence dans moins de 7 jours) et toutes les semaines commencées sont **figés** : ajouter, corriger, retirer ou importer des thèmes ne modifie jamais un thème déjà attribué, seulement les semaines encore lointaines. Un thème déjà utilisé (ou d'une partie privée) est immuable et ne peut être ni modifié ni retiré. Les anciennes histoires gardent leur thème d'origine jusqu'à leur suppression (2ᵉ lundi suivant leur début).

**Mise en service.** Appliquer 0011 puis 0012 (`npm run db:apply`) ne change pas le thème actif : le nouveau système prend le relais au prochain lundi. Les joueurs ne peuvent lire que les thèmes des semaines commencées : les prochains cartons restent secrets (réservés à l'administration).

**Gérer la banque** sans redéploiement : onglet « Banque de thèmes » de `#/admin` (mêmes droits que le reste de l'administration, revérifiés côté serveur) : consulter tous les thèmes avec leur statut (libre, programmé, utilisé), chercher, ajouter, corriger ou retirer un thème inutilisé, voir les prochains cartons et importer une liste (un titre par ligne ou JSON, avec détection des doublons exacts — accents, majuscules, ponctuation et articles ignorés — et des titres trop proches avant confirmation). Pour de vrais cartons de feuilles d'arbitre, choisir la provenance « Feuille de match (arbitre) ». En ligne de commande : ajouter les titres dans `supabase/themes.json` puis `npm run db:themes` et coller le SQL affiché dans l'éditeur SQL (les doublons sont ignorés).

### Les Mimo et le texte libre (éditeur)

Deux outils de mise en scène, disponibles sur **toutes les plateformes** (téléphone, iPad, ordinateur, souris, écran tactile): « + Mimo » et « + Texte », à côté du stylo et de la gomme. On peut en placer **autant qu'on veut** dans une même case, en alternant avec le dessin libre. Ils partagent la même logique: un seul objet manipulable à la fois, « Placer » le fusionne en **pixels noirs** dans l'image aplatie (une entrée d'historique, comme un trait: annuler le retire, rétablir le remet), « Annuler » l'abandonne. Rien n'est stocké à part: seul le PNG aplati est publié.

- **Manipulation (commune).** Glisser déplace; pincer (deux doigts), tourner la molette ou tirer la poignée du coin bas droit change la taille, proportions conservées. Un appui bref agit sur l'objet. Tant qu'il n'est pas placé, rien ne dessine sur la toile; cadre et poignée ne sont jamais dans l'image (`src/editor/mimo/gesture.ts`).
- **Mimo.** Petits personnages originaux au trait noir (6 styles × 6 émotions × 6 poses). Un appui sur le Mimo change sa pose; l'émotion et le style se changent dans deux zones dédiées sous la toile (glisser, ou toucher une moitié: déplacer et balayer sur le même objet se confondaient). Dessin vectoriel déterministe (`src/editor/mimo/art.ts`), rasterisé sans lissage (`raster.ts`), identique à l'aperçu au pixel près. `npm run mimo:sheet -- /tmp/mimo.png --size=150` produit des planches contact. Animations de moins de 250 ms, désactivées si le système demande moins d'animations.
- **Texte.** « + Texte » ouvre un champ (le clavier s'ouvre tout de suite, la console suit le bas de la zone visible), le texte apparaît en noir sur la toile à mesure qu'on écrit, sans bulle ni cadre. Une seule police, dessinée au trait dans le jeu (`src/editor/text/font.ts`): lettres rondes et épaisses, majuscules et minuscules, accents français (œ compris), chiffres et ponctuation; aucun fichier de police, rendu identique partout. Retours à la ligne respectés, passage à la ligne automatique, 100 caractères au plus (le compteur n'apparaît qu'en approchant de la limite), texte toujours entièrement dans la toile. Sur ordinateur: Entrée = nouvelle ligne, Ctrl/Cmd+Entrée = placer, Échap = annuler.

### Décor (menu « Outils »)

« Outils » > « Décor » tire un **lieu au hasard** (dix: chambre, cuisine, rue, forêt, plage, classe, bureau, parc, espace, restaurant), au trait noir, sans remplissage, un seul dessin fixe par lieu (`src/editor/decor/art.ts`). Chaque lieu est composé d'éléments indépendants (le lit, la fenêtre, l'armoire…). Disponible sur toutes les plateformes; ce n'est pas une entrée de la barre principale.

- **Commandes.** **Un tap (ou un clic) sur le décor fait « Change ! »**, comme un tap change la pose d'un Mimo: un autre lieu est tiré (jamais le même que le précédent), en gardant position et taille et en remettant les éléments retirés. Il n'y a pas de bouton dédié. « Gommer » bascule en mode retrait: un toucher ou un clic retire **l'élément entier** le plus proche (zone tolérante au doigt, en pointillés à l'écran; le vide ne retire rien; le décor ne bouge plus dans ce mode); la flèche arrière remet le dernier élément retiré. « Placer » fusionne, « Annuler » abandonne. Glisser déplace, pincer, tourner la molette ou tirer la poignée (toujours atteignable, même pour un grand décor) change la taille, de 90 à 560 pixels de large, proportions 4:3; il peut dépasser de la toile.
- **Toujours derrière le dessin.** Un décor ne trace que sur les pixels **blancs**: tout pixel déjà dessiné (couleur, trait noir, Mimo, texte) reste intact. De plus, un Mimo ou un texte placé enregistre une zone protégée (`Project.shield`, un simple masque qui suit l'historique, jamais affiché ni publié; `src/editor/shield.ts`): le Mimo est protégé en entier, visage et corps compris, avec 2 pixels de marge, le texte avec un halo proportionnel à sa taille. Un décor ajouté ensuite passe donc derrière eux sans les traverser.
- **Limites connues.** Le blanc dessiné au crayon blanc ou à la gomme est indiscernable du fond: le décor y apparaît. Un décor placé **avant** un Mimo ou un texte reste visible à travers eux (les Mimo sont des contours sans fond): pour mettre le décor derrière une scène, l'ajouter après. Déplacer une sélection avec « Bouger » ne déplace pas sa zone protégée.
- **Mêmes règles que les Mimo et le texte.** Un seul objet manipulable à la fois, aucun calque, une entrée d'historique par placement (annuler et rétablir), nombre de décors illimité, rendu identique dans l'aperçu, la publication et l'export.

### Survivor (laboratoire expérimental)

Mode hors ligne et solo, **absent de l'accueil et de la navigation**: on l'ouvre uniquement par l'adresse `#/lab/survivor` (chargé à la demande, `src/survivor/`). Le Cadavre Exquis classique n'est pas modifié: l'éditeur est le même (`EditorWorkspace`), avec une comptabilité d'encre **désactivée par défaut** (`EditorSession.ink = null`, tout est gratuit).

- **Principe.** Aucune intelligence artificielle ni validation: la demande narrative est une perturbation créative que le joueur choisit d'intégrer à son histoire; le jeu n'arbitre que les ressources.
- **Boucle.** 16 cases de BD, un thème tiré de `supabase/themes.json`. Avant chaque case, l'éditeur propose **trois demandes** (une facile, une intermédiaire, une difficile): le choix ouvre directement l'éditeur, qui garde la demande et sa récompense affichées. Terminer la case verse automatiquement l'encre de la demande (+10, +20 ou +35, plus Narrateur et Régénération, plafonnée par la capacité) et affiche brièvement le gain. Toutes les 2 cases, une amélioration à choisir parmi 3 (`upgrades.ts`): Encrier, Plume légère, Ami imaginaire, Architecte, Écrivain, Recyclage, Régénération, Joker (renouvelle les trois demandes avant de dessiner), Narrateur (+5 par exemplaire sur la récompense), Dernier souffle.
- **Demandes.** Les 36 entrées de la table « Les demandes déraisonnables de l'éditeur » de Manga Relay (annexe 2, traduites en français, identifiants = résultat des deux dés; `src/survivor/constraints.ts`). Le classement par difficulté et l'éligibilité par étape (introduction, complications, escalade, dénouement: pas de retour d'un ancien personnage à la case 1, pas de trahison au début, pas d'annonce de suite à la fin…) sont des tables provisoires en tête de ce fichier. Une demande déjà choisie n'est pas reproposée tant qu'il en reste d'inédites; les demandes seulement proposées peuvent revenir. **Vérifier que la licence de Manga Relay autorise cette reprise avant toute diffusion.**
- **Encre.** Une réserve unique de 100 (jauge visible en temps réel, avec le coût prévu d'un objet en attente). Trait: longueur × épaisseur × densité de la texture; pot de peinture selon la surface; coût fixe pour Mimo, texte, décor et tampon. La gomme est gratuite et ne rend rien (sauf Recyclage). Annuler rend le coût, rétablir le dépense à nouveau. Une action impossible à payer est grisée; un trait s'arrête net quand la réserve est vide.
- **Fin.** Victoire à la case 16. Défaite si plus d'encre, plus de Mimo gratuit, plus de Dernier souffle et une case trop vide pour être terminée. L'écran final montre la BD, les cases terminées, les demandes choisies par difficulté, les améliorations et l'encre consommée, avec export PNG (planche 4×4) et « Recommencer ».
- **Équilibrage.** Tout est dans **`src/survivor/config.ts`** (valeurs provisoires, récompenses comprises).
- **Sauvegarde.** Uniquement dans `localStorage` (clé `cl.survivor.v1`, format 2): cases terminées, progression, trois demandes proposées et choix fait (recharger ne renouvelle pas gratuitement les demandes), jamais le dessin en cours (reprendre repart d'une case vierge). Une partie de l'ancien format (contrainte imposée et auto-validée) est migrée à la lecture, cases conservées. Le menu relit toujours la dernière sauvegarde.
- **Limites connues.** Copier/coller et déplacer une sélection ne coûtent rien (faille à fermer si le mode sort du labo); la défaite est rare car les récompenses ne descendent pas sous +10; seuil minimal pour terminer une case (60 pixels) à rééquilibrer; non testé sur de vrais appareils.

### Survivor multijoueur (fondations, étape 1/5)

Toujours caché dans `#/lab/survivor` (menu « Multijoueur · expérimental »); le Solo reste local et le Cadavre Exquis classique n'est pas touché. Relay, Duel et Battle reposent sur une infrastructure serveur (étape 1) et sont jouables depuis l'étape 2.

- **Migration** `supabase/migrations/0013_survivor_multiplayer.sql` (tables `survivor_games`, `_players`, `_cases`, `_reservations`, `_invites`; seule dépendance: `profiles` et `themes`). Non appliquée automatiquement. Test: `npm run db:check`. Application sur un projet **de test**: mettre l'URL de ce projet dans `SUPABASE_DB_URL` (`.env.local`) puis `npm run db:apply` (elle applique toutes les migrations en attente de cette base); ou coller le fichier dans l'éditeur SQL.
- **Autorité serveur.** Aucune écriture directe (RLS sans politique d'écriture, droits retirés); tout passe par des RPC `SECURITY DEFINER` à `search_path` figé, qui lisent l'identité dans `auth.uid()`. Fonctions internes fermées à tous les rôles. Lecture réservée aux participants; en Duel, les cases adverses ne sont lisibles qu'à la fin. Aucune clé `service_role` côté client.
- **Paramètres** (source unique, `survivor_rules()`, lus par l'interface): Relay 16 participants, réservation 15 min (prolongation par pas de 10 min, 45 min au total); Duel 3 parties non terminées, 72 h après appariement; Battle 5 parties non terminées, 24 h par tour. Chaque partie en fige une copie à sa création. Thème et seed (tirés par le serveur) sont immuables (trigger).
- **États.** Partie: `searching → active → finished | abandoned`, `searching → cancelled` (transitions légales imposées par trigger); joueur: `playing | done | forfeited`; tour: déduit (Battle: `turn_player`, Relay: réservation). L'état, la catégorie (« à toi de jouer », « en attente », « terminées ») et les actions autorisées sont calculés par `survivor_view`; l'interface ne les recalcule pas. Les délais dépassés sont appliqués à chaque appel par `survivor_expire_due()` (idempotent, heure serveur, aucune tâche planifiée): forfait du joueur dont le tour expire (Battle), forfait de ceux qui n'ont pas fini (Duel).
- **Matchmaking** (`survivor_matchmake`, asynchrone, idempotent, sans polling ni WebSocket). Relay: réserve la prochaine case d'une partie éligible (pas la sienne, pas complète, pas déjà réservée), en privilégiant les parties les plus avancées, puis les plus anciennes et les plus longtemps sans contribution; sinon en crée une. Duel/Battle: rejoint le plus ancien défi ouvert qui n'est pas le sien, sinon crée un défi persistant (le premier joueur d'une Battle est tiré au sort). Invitations: jeton de 64 caractères hexadécimaux, acceptation atomique, lien `#/lab/survivor/invite/<jeton>`.
- **Cases.** Voir l'étape 2 ci-dessous: `survivor_submit_case` a changé de contrat (le serveur calcule récompense et réserve).
- **Limites.** Les accès réellement concurrents (verrous, `SKIP LOCKED`) ne sont pas testés (PGlite n'a qu'une connexion; les courses sont simulées par entrelacement et contraintes d'unicité); rien n'a été testé contre un vrai projet Supabase ni depuis l'interface (le serveur n'était pas joignable pendant les essais); le chemin d'image n'est pas vérifié dans le stockage; pas de limite de débit; un Relay sans activité n'expire jamais.

### Survivor multijoueur: gameplay (étape 2/5)

Relay, Duel et Battle sont jouables depuis `#/lab/survivor` avec le même éditeur (`EditorWorkspace`/`EditorSession`), la même jauge, les mêmes 36 demandes et les mêmes dix améliorations que le Solo (inchangé, hors ligne). Les modes multijoueurs demandent une connexion.

- **Migration** `0014_survivor_gameplay.sql` (complète 0013 sans la réécrire; changement de contrat de `survivor_submit_case`). Nouvelles tables `survivor_runs` (réserve, capacité, améliorations, charges de Joker et de Dernier souffle, demandes proposées et choisie, offre d'amélioration, étape du tour, demandes transmises), `survivor_constraints` et `survivor_upgrade_defs`, `survivor_rate_limits`; bucket privé `survivor`. Rien n'est lisible directement dans ces tables: tout passe par les RPC, dont `survivor_state` (état complet) et les actions `survivor_pick`, `_joker`, `_use_emergency`, `_choose_upgrade`, `_set_demands`, `_declare_stuck`, `_submit_case`.
- **Une run par réserve.** Relay: une run commune. Duel et Battle: une par joueur. L'étape (`choosing`, `upgrade`, `demands`, `waiting`, `finished`) et chaque décision sont enregistrées: fermer ou recharger la PWA ne rejoue rien. Chaque action rejouée est idempotente (identifiant de soumission, compteurs d'utilisation du Joker et du Dernier souffle, état déjà atteint).
- **Économie côté serveur.** À la soumission, le serveur vérifie la position attendue, que la demande est celle choisie parmi les propositions, que la dépense est un nombre fini borné par la réserve, puis calcule récompense (10/20/35 + Narrateur), régénération, plafonnement, amélioration due (toutes les 2 cases *personnelles*), transition et fin de partie. Il ne reçoit plus aucune récompense du client.
- **Tirages déterministes.** Pas de générateur à état: chaque tirage est une fonction de la seed du serveur (exposée en texte, sans perte de précision), de la position, de la difficulté et d'un « sel » (`0` normal, `jN` pour le Nième Joker; offres d'amélioration indexées à part). Un Joker ou un tirage de l'adversaire ne décale donc jamais les suivants; les propositions ne diffèrent que si l'historique des choix rend certaines demandes inéligibles. Les propositions sont enregistrées: recharger ne les renouvelle pas.
- **Relay.** Réservation de 15 min (prolongée pendant le dessin, 45 min au plus; quitter une case n'entame pas l'encre). Une amélioration due est choisie par l'auteur de la case; passé son délai (celui d'une réservation), le joueur suivant la choisit avant de dessiner, donc la BD n'est jamais bloquée. Victoire collective à 16 cases; défaite collective si le détenteur de la case déclare la panne d'encre (sans Dernier souffle ni Ami imaginaire).
- **Duel.** Mêmes seed, thème et premières propositions pour les deux joueurs, réserves et améliorations individuelles, avancement indépendant. Les dessins adverses sont fermés tant que le Duel n'est pas fini, **au niveau des politiques RLS et du stockage** (pas seulement de l'interface). La fin affiche les performances des deux joueurs (cases, encre, demandes, améliorations, panne d'encre); aucun vainqueur artistique: le départage viendra avec les arbitres (étape 3).
- **Battle.** Une BD commune, deux réserves visibles (la mienne en jaune, celle de l'adversaire en rose). Le premier joueur est tiré au sort. Un tour = case, amélioration éventuelle, trois demandes (facile, intermédiaire, difficile, éligibles à la progression de l'histoire) pour l'adversaire; chaque étape est reprise après interruption et le délai de 24 h ne repart qu'à la transmission. Le Joker du joueur qui reçoit les demandes les remplace par un tirage aléatoire. Panne d'encre = défaite; forfait = victoire de l'adversaire; deux survivants à la 16e case = égalité provisoire.
- **Stockage.** Chemin `<joueur>/<partie>/<soumission>.png` dans le bucket privé `survivor` (PNG, 256 Ko). Dépôt réservé aux participants (ou au détenteur d'une réservation Relay); la soumission vérifie que le fichier existe, appartient au joueur, correspond à la partie et à la soumission et respecte taille et type. Ni mise à jour ni suppression: un dessin publié est immuable. Une relance après un échec réutilise le même identifiant (un dessin modifié en prend un nouveau): jamais deux cases ni deux récompenses. Les fichiers jamais publiés sont mis en file de suppression de façon opportuniste par `survivor_queue_orphans` (même garde que les autres purges: inactive tant que `enable_expiry_purge` n'est pas armé; aucun service permanent).
- **Cohérence SQL ↔ TypeScript.** La banque de demandes (difficulté, étapes), les améliorations, les récompenses et les valeurs d'améliorations sont **générées** depuis la configuration TypeScript (`npx vite-node scripts/survivor-sql.ts`) dans un bloc de la migration; un test unitaire échoue si ce bloc diverge. Les formules sont linéaires et le test SQL en vérifie les résultats (10/20/35, +5, +4, plafonds, charges). Restent dupliqués, avec des tests des deux côtés: l'éligibilité narrative et les étapes de l'histoire.
- **Ce que le serveur ne peut pas vérifier (limites assumées).** (1) Le **coût de dessin** est calculé par l'éditeur local: un client modifié peut sous-déclarer sa dépense (le serveur la borne seulement par la réserve; pas de rejeu des gestes). (2) La **panne d'encre** est déclarée par le client; elle est refusée tant qu'un secours existe, ne nuit qu'au déclarant en Duel et en Battle, mais en Relay le détenteur de la case peut terminer la BD de façon abusive. (3) Le **contenu** du PNG n'est pas inspecté (seuls taille et type MIME le sont). (4) Le limiteur d'appels (par joueur et par action, par minute) ne compte que les appels réussis. Rien de tout cela n'est présenté comme une garantie anti-triche.
- **Tests.** `npm run db:check` (parties Relay, Duel et Battle complètes, réserves, récompenses, améliorations, tirages, reprises, doubles soumissions, expirations, pannes, forfaits, confidentialité des cases et des fichiers, stockage, orphelins, limiteur) et `npx vitest run`. Les courses réellement concurrentes et le stockage réel de Supabase **ne sont pas testés** (PGlite: une seule connexion; `storage.objects` y est simulé).
- **Tester avec Supabase (projet de test, jamais la production).** 1) Créer un projet de test, activer les connexions anonymes. 2) `SUPABASE_DB_URL=<url du projet de test>` dans `.env.local`, puis `npm run db:apply` (applique 0013 et 0014). 3) Vérifier dans Storage que le bucket `survivor` est privé (PNG, 256 Ko). 4) `VITE_SUPABASE_URL` et `VITE_SUPABASE_PUBLISHABLE_KEY` vers ce projet, `npm run dev`, ouvrir `#/lab/survivor` dans deux navigateurs (deux comptes anonymes) et jouer un Duel et une Battle de bout en bout. 5) Pour de vraies sessions concurrentes: lancer deux transactions `psql` appelant `survivor_matchmake('duel')` en parallèle.
- **Intégration du futur mode Arbitre (étape 3).** Chaque case conserve `author_id`, `constraint_id` (donc sa difficulté), `ink_spent`, `ink_reward` et `submission_id`; `survivor_games.ended_reason`, `forfeit_by` et `defeat_by` donnent les causes de fin. Pour juger un Duel, lire les deux BD via `survivor_can_read_case` après la fin (ou ajouter un rôle d'arbitre à cette fonction et à `survivor_can_read_file`); les votes se rattacheront à `survivor_cases.id`.

### Survivor: Arbitre et encre bonus (étape 3/5)

Cinquième activité de `#/lab/survivor` (carte « Arbitre » du menu): lire les BD des autres et juger **le respect de la contrainte, jamais le talent**. Aucune IA, aucune analyse automatique des dessins. Migration `0015_survivor_arbiter.sql` (complète 0013 et 0014, non déployée).

- **Soumission.** Solo: bouton facultatif « Soumettre aux arbitres » sur l'écran final (en ligne; seules les cases terminées, leurs demandes et une déclaration `claimed` partent; les performances Solo ne sont jamais certifiées). Relay, Battle et Duel: bouton sur l'écran de fin d'une partie **terminée** (victoire, défaite ou égalité; pas les forfaits). Au moins 4 cases terminées (défaite incomplète admise). Les images ne sont jamais copiées: `survivor_bd_cases` référence les PNG existants du bucket privé. Les contributeurs doivent accepter (« Demandes d'arbitrage » dans le menu Arbitre); la partie n'attend personne et une décision est définitive. En Duel, chaque auteur consent pour sa BD; si l'autre refuse, la BD restante est arbitrée seule.
- **Attribution** (`survivor_arbitrate_next`, jamais choisie par le joueur). Priorité: moins d'arbitrages (en cours compris), plus anciennes, puis auteurs jamais rencontrés. Exclues: ses propres BD, les BD collectives et les Duels auxquels il a participé, celles qu'il a déjà arbitrées ou abandonnées, celles qui ont atteint leur maximum (3), signalées, masquées, refusées ou en attente de consentement. Une attribution est enregistrée et reprise telle quelle; une attribution inachevée depuis plus d'une heure ne compte plus contre la capacité (donc une BD n'est jamais verrouillée), et si le maximum est déjà atteint à la validation, l'arbitrage se ferme sans récompense.
- **Lecture.** Les tables d'arbitrage sont fermées à tous les clients (RLS sans politique). L'arbitre ne lit que par RPC une BD anonymisée (thème, cases, demandes, progression; ni auteur, ni votes des autres, ni popularité, ni gains) et, côté stockage, uniquement les images de son attribution **en cours** (`survivor_can_read_file` élargie à ce seul cas; `survivor_can_read_case` inchangée), via des URL signées temporaires. Il perd l'accès à la fin.
- **Votes.** Pouce levé = contrainte respectée, pouce baissé = non respectée; modifiables et effaçables jusqu'à la validation, strictement limités aux cases de l'attribution, jamais pour ses propres cases. « Passer cette BD » ou la signaler (le premier signalement la masque, rétablie par `survivor_admin_bd_status`) arrête l'arbitrage sans récompense et efface les votes provisoires. Les signalements Survivor sont propres à Survivor: ceux du jeu classique portent sur des contributions et ne sont pas compatibles.
- **Récompenses** (centralisées dans `survivor_arbitration_rules()`, calculées au serveur, versées une seule fois à la validation complète): +2 par case jugée (up ou down, identique), +10 pour l'arbitrage complet, +5 à **l'auteur réel de chaque case** par upvote reçu, rien pour un downvote, jamais de retrait. Une BD de 16 cases rapporte donc 42 à son arbitre. Limite de 5 arbitrages complets par compte et par jour (Europe/Paris).
- **Registre d'encre bonus** (`survivor_ink_ledger`, `survivor_wallets`). Écritures par RPC seulement, lignes immuables, clé d'idempotence unique par gain (arbitrage + case, ou bonus), solde tenu à jour par trigger. Chacun ne lit que son solde et son historique (`survivor_wallet`). À l'étape 3 aucune dépense n'existait; l'étape 4 (0016) ouvre les débits.
- **Duel.** Les deux BD sont arbitrées ensemble (ordre aléatoire A/B, même arbitre, mêmes arbitrages complets). Après 3 arbitrages complets, le verdict narratif compare le total d'upvotes (une case manquante ne rapporte rien): victoire ou égalité, définitif, séparé de la survie et des forfaits, qui ne sont jamais modifiés. Sans les deux BD arbitrées, aucun vainqueur narratif. Solo, Relay et Battle: les votes ne changent aucune issue.
- **Correctif lié.** Une partie qui se termine libère désormais ses réservations Relay (sinon `survivor_matchmake` pouvait renvoyer une partie finie pendant 15 minutes).
- **Tester sur Supabase** (projet de test, jamais la production): `npm run db:apply` applique 0013 à 0015 sur la base de `SUPABASE_DB_URL`; jouer un Relay, un Duel et une Battle jusqu'à la fin (au moins 4 cases ou une défaite), soumettre, accepter avec le second compte, puis arbitrer avec trois autres comptes anonymes. Vérifier dans Storage que les URL signées de l'arbitre expirent et qu'un autre compte reçoit un refus.
- **Limites assumées.** (1) Le chemin d'une image contient l'identifiant (pas le pseudonyme) de son auteur et apparaît dans l'URL signée: l'anonymat de l'arbitre est celui de l'interface, pas du stockage. (2) **Comptes anonymes multiples**: rien n'empêche un joueur d'en créer plusieurs pour gagner 2 d'encre par case (le plafond quotidien est par compte). (3) **Ententes**: deux comptes peuvent s'échanger des upvotes. (4) **Votes aléatoires** pour l'encre: la rémunération est volontairement indépendante du sens du vote, donc rien ne distingue un vote réfléchi d'un vote au hasard. (5) Un signalement unique masque une BD: un arbitre malveillant peut en masquer (rétablissement par l'administration). (6) Un consentement non donné reste en attente indéfiniment. (7) Les BD Solo ne sont ni certifiées ni limitées dans leur contenu au-delà du format et de la taille des PNG. Pas de réputation, de classement, de notification ni de galerie.
- **Tests.** `npm run db:check` couvre soumission Solo, éligibilité et consentement, attribution et exclusions, lecture des cases et des images, reprise, votes, récompenses (arbitre identique pour up et down, auteur réel de chaque case, aucune pénalité, bonus, idempotence), limites (maximum, quotidienne, attribution unique), départage de Duel (victoire, égalité, forfait intact, BD seule), registre, droits; `npx vitest run` couvre le client. **Non vérifiés en conditions réelles**: accès concurrents (verrous `SKIP LOCKED` et consultatifs; PGlite n'a qu'une connexion), autorisations du stockage de Supabase, fonctionnement de bout en bout (l'interface n'a été essayée que contre un faux serveur dans le navigateur).
- **Intégration de l'étape 4** (dépenses d'encre bonus). Ajouter des écritures négatives au registre (`reason` supplémentaires, `check (amount > 0)` à relâcher, solde ≥ 0 déjà garanti par `survivor_wallets.balance`), les débiter par RPC avec la même clé d'idempotence; lire le solde via `survivor_wallet` / `survivor_hub`; les avantages de départ se brancheront sur `survivor_ensure_run` (réserve et améliorations initiales).

### Survivor: encre bonus, consommables (étape 4/5)

L'encre bonus gagnée en arbitrant (étape 3) peut maintenant se **dépenser**, en Solo et en Relay seulement. Migration `0016_survivor_shop.sql` (complète 0013 à 0015, non déployée). L'encre bonus (étoile, portefeuille permanent) est distincte de l'encre de dessin (jauge d'une partie). Les récompenses d'arbitrage ne changent pas.

- **Catalogue** (`survivor_shop_rules()`, source unique; l'interface n'en garde aucune copie: elle lit prix, effets, limites et solde via `survivor_shop`). **Recharge** 40: +20 d'encre de dessin pendant le choix de la demande, jamais au-delà de la capacité, seulement s'il manque au moins 20. **Joker** (`constraint_reroll`) 30: trois nouvelles demandes (les charges de Joker acquises ne sont pas touchées). **Second choix** (`upgrade_reroll`) 25: trois autres améliorations à la place des trois proposées (jamais une en plus, jamais une déjà vue). **Dernière chance** (`emergency_refill`) 60: +25 d'encre pendant la case, sans perdre le dessin; indépendante du Dernier souffle gratuit.
- **Limites.** Solo: 2 achats par partie; Relay: 3 par BD (partagés par l'équipe); chaque consommable une seule fois par partie. Duel et Battle: refusés **côté serveur** (`SHOP_NOT_ALLOWED`) même avec du solde, pour garder des conditions identiques. En Relay, seul le joueur qui joue la case achète, à la bonne étape, et l'effet profite à toute l'équipe; seul son portefeuille est débité.
- **Garanties transactionnelles** (`survivor_buy`). Une seule transaction: vérifications, verrous, débit du registre, effet, reçu; tout échoue ensemble. Ordre des verrous, jamais inversé: **partie → run → portefeuille** (Relay) ou partie Solo → portefeuille. Le client n'envoie qu'un identifiant d'achat, clé d'idempotence unique: rejouer (double clic, réponse perdue) renvoie le reçu initial sans nouveau débit. Le registre accepte les dépenses (montants négatifs, `item` et partie nommés), reste immuable, et le solde ne descend jamais sous 0 (vérification de l'achat **et** contrainte `survivor_wallets.balance >= 0`). L'historique (`survivor_wallet`) montre gains et dépenses.
- **Solo.** La partie reste locale; le serveur ne connaît que son identifiant stable (`survivor_solo_games`, ajouté aux anciennes sauvegardes au chargement) pour appliquer les limites. Le serveur rend un **reçu**; le moteur local l'applique une seule fois par reçu (`SurvivorGame.applyPurchase`). L'achat est marqué « en cours » dans la sauvegarde avant l'envoi: si la réponse se perd (fermeture, réseau), `survivor_buy_check` retrouve le reçu au rechargement (ou prouve que le serveur n'a rien reçu). Un refus définitif libère l'attente; une erreur réseau la conserve. Hors ligne ou sans compte, la partie reste jouable et aucune offre n'apparaît; le Solo n'ouvre pas de compte de lui-même.
- **Interface.** Offres en contexte, avec prix et confirmation (solde avant → après): Recharge et Joker au choix de la demande, Dernière chance quand l'encre manque pendant le dessin, Second choix sur l'écran d'amélioration. Rien n'est annoncé avant la confirmation du serveur; en Relay, l'état affiché est celui que le serveur renvoie.
- **Tester sur Supabase** (projet de test, jamais la production): `npm run db:apply` (0013 à 0016); gagner de l'encre en arbitrant (étape 3), puis acheter en Solo (réponse coupée dans les outils réseau, puis recharger: l'achat est retrouvé sans double débit), en Relay avec deux comptes, et vérifier le refus en Duel/Battle. Contrôler que `survivor_wallets.balance` = somme du registre.
- **Limites assumées.** (1) Le Solo est local: un joueur peut modifier sa sauvegarde et se donner l'effet sans payer (le serveur ne peut ni voir ni vérifier la partie); seuls la dépense, les plafonds d'achats et la limite « une fois par type » sont garantis côté serveur. (2) Un identifiant de partie Solo est choisi par le client: un client modifié peut changer d'identifiant de partie Solo pour repartir à zéro achat (limite de 2 contournable, seul le solde borne la dépense). (3) Les conditions locales (dessin, charges) d'un achat Solo ou de la Dernière chance Relay ne sont pas vérifiables au serveur; seules l'étape et le joueur le sont. (4) Les comptes anonymes multiples et les ententes (étape 3) restent possibles. (5) Aucun remboursement. Pas de boutique générale, d'avantages de départ ni de nouveaux modes.
- **Tests.** `npm run db:check` couvre catalogue, solde insuffisant, idempotence (rejeu et double clic), limites par mode et par type, refus Duel/Battle, atomicité (rien débité si l'effet échoue), effets Relay (réserve plafonnée, demandes et offre renouvelées), immuabilité du registre, solde = somme du registre, `survivor_buy_check`, droits, et la concurrence **simulée**; `npx vitest run` couvre l'application locale des reçus (idempotence, plafonds, Joker acquis intact, anciennes sauvegardes, achat en cours après rechargement), les appels (aucun prix ni effet envoyé), la cohérence interface/migration et l'historique. **Non vérifiés en conditions réelles**: concurrence (PGlite n'a qu'une connexion, donc l'ordre des verrous n'est pas éprouvé), déploiement sur Supabase, bout en bout contre la vraie base.
- **Intégration de l'étape 5.** Les avantages de départ se brancheront sur `survivor_ensure_run` (réserve initiale) et de nouveaux consommables s'ajoutent dans `survivor_shop_rules()` et la branche d'effet de `survivor_buy`, sans toucher au registre; l'interface lit le catalogue du serveur.

### Signalements

Publication immédiate, sans approbation. « Signaler ce dessin » (fiche d'une case et lecture d'une histoire) propose cinq motifs et une précision facultative. Le premier signalement valide masque le dessin au public (« Dessin temporairement masqué ») : l'image n'est plus exposée par la vue, les cases des autres auteurs et la structure sont conservées, la case ne peut plus être continuée directement (`PARENT_HIDDEN`) et rien n'est détruit. Interdit : signaler son propre dessin ou le même dessin deux fois ; limite de 10 signalements par heure et par joueur ; les signalements d'un compte bloqué sont enregistrés sans effet. Un dessin rétabli n'est pas remasqué par d'anciens signalements : trois nouveaux signalements ouverts, postérieurs au rétablissement, sont nécessaires. Limites connues : le bucket `previews` est public, donc un fichier masqué reste lisible par quelqu'un qui connaît déjà son URL jusqu'à sa suppression définitive ; des comptes anonymes en nombre peuvent contourner la limite par joueur (d'où le blocage manuel).

## Récompenses et tampons

Deux plaisirs sont récompensés, sans monnaie, XP, classement ni série quotidienne :

- **Histoires collectives terminées** : quand la case 4 d'un chemin est publiée, chaque auteur distinct du chemin (cases 1 à 4) reçoit +1, une seule fois même s'il a dessiné deux cases. Chaque case 4 est une histoire distincte, donc un embranchement qui aboutit ailleurs compte à part. Une branche inachevée ne rapporte rien.
- **Histoires inspirées** : l'auteur de la case 1 reçoit +1 pour chaque histoire terminée qui en descend (compteur total par joueur, et par première case via `story_credits.root_id`). Les deux compteurs sont indépendants : l'auteur d'une case 1 profite des deux.

Tout est calculé par le serveur dans la transaction de `publish_contribution` (`credit_story`), idempotent (clé primaire `(case 4, joueur, nature)`), sûr en cas de publications simultanées, et sans effet si le chemin contient une case masquée ou retirée par la modération ; un dessin rétabli ensuite déclenche le crédit. L'administration peut retirer les récompenses d'une histoire abusive (`admin_revoke_story`), qui ne sera plus jamais recréditée ; les tampons déjà débloqués restent acquis. Limite connue : des comptes anonymes en nombre pourraient s'envoyer des histoires, comme pour les signalements ; seul le débit maximal de publication s'applique.

**Les récompenses survivent à l'expiration.** Les tables de récompenses ne référencent pas les contributions (aucune clé étrangère) : après la suppression d'un thème, les compteurs, les tampons et l'historique minimal (identifiants) restent acquis. Seules les nouveautés qui renvoyaient aux dessins supprimés sont marquées « disparues » (déclencheur sur la suppression des contributions) et n'ouvrent plus aucune page ; les notifications push associées sont déjà nettoyées par la purge.

**Tampons.** Six dès le départ ; huit se débloquent automatiquement :

| Histoires terminées | Tampon | Histoires inspirées | Tampon |
|---|---|---|---|
| 1 | Explosion | 1 | Moustache |
| 3 | Effet de vitesse | 3 | Lunettes |
| 5 | Nuage de fumée | 5 | Chapeau extravagant |
| 10 | Fantôme | 10 | Masque mystérieux |

Plusieurs seuils atteints d'un coup se présentent dans une seule fenêtre « Nouveau tampon débloqué ! ». Les paliers « Ton dessin a inspiré N histoires différentes ! » sont 3, 5 et 10 pour une même case 1.

**Configuration centralisée** : `src/domain/stickers.ts` (seuils, paliers, limite et tailles de tampon, pixel art 16 × 16 en six couleurs). Le serveur applique ses propres copies (`sticker_rules`, `reward_config`) : après avoir modifié un seuil, lancer `npm run db:stickers` et exécuter dans l'éditeur SQL la commande affichée (`sync_reward_rules`, qui réévalue tous les joueurs et ne retire jamais un tampon acquis). Un test vérifie que la configuration et la migration restent identiques.

**Présentation.** Auteur de la case 4 : l'écran de publication révèle les quatre cases dans l'ordre (la dernière mise en valeur), avec confettis pixel art, « Votre histoire est terminée ! », « Une nouvelle BD à plusieurs est née ! », les auteurs sans doublon, « +1 histoire collective terminée » et « Passer l'animation ». Autres auteurs : « Mes dessins » > « À fêter » regroupe, sans enchaîner d'animations, « Une histoire à laquelle tu as participé est terminée ! » (ouvre `#/finished/<case 4>`), les paliers d'inspiration avec les miniatures des fins qui existent encore, et les tampons débloqués (fenêtre ouverte automatiquement une fois par session, jamais dans l'éditeur). Une pastille s'ajoute à celle des réponses. « Ma collection » (compteurs, tampons verrouillés avec leur condition) et « Mes histoires terminées » restent discrets. Aucune notification push supplémentaire ; pas de son ; `prefers-reduced-motion` supprime confettis et révélations.

**Mise en service** (aucune opération destructive) : appliquer `0010_rewards.sql` (`npm run db:apply`). La migration rattache les histoires déjà terminées sans double comptage (relançable avec `select public.backfill_story_credits();`) et sans nouveauté « histoire terminée » ; les tampons ainsi débloqués sont annoncés dans « Mes dessins ». Aucune tâche planifiée ni fonction Edge nouvelle.

## Déploiement sur GitHub Pages

Le workflow `.github/workflows/deploy.yml` construit et publie l'application à chaque push sur `main` (typecheck et tests d'abord).

1. Dépôt GitHub > Settings > Pages > Source : **GitHub Actions**.
2. Settings > Secrets and variables > Actions > **Variables** : `VITE_SUPABASE_URL`, `VITE_SUPABASE_PUBLISHABLE_KEY`, `VITE_VAPID_PUBLIC_KEY` (valeurs publiques par conception; ne jamais publier la clé `service_role` ni la clé privée VAPID).
3. Supabase > Authentication > URL Configuration : ajouter `https://<compte>.github.io/<dépôt>/` aux URL autorisées (liens e-mail).
4. Le site est servi sous `/<dépôt>/` (variable de build `VITE_BASE`); avec un domaine personnalisé, mettre `VITE_BASE` à `/` dans le workflow.

Le routeur par hash évite toute configuration de redirection côté serveur; les notifications push et le service worker fonctionnent en HTTPS, ce que fournit GitHub Pages.
